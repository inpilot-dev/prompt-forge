## 실패 시 즉시 중단하는 절차 커맨드 (fail-fast-command-chain)
- **단계:** 구현위임
- **언제:** 여러 단계가 순서대로 물려 있는 반복 운영 절차(데이터 추가·마이그레이션·릴리스 점검 등)를 커맨드 하나로 굳힐 때.
- **Bad:** "문제 추가하고 검증도 하고 백업도 해줘." (중간 단계가 조용히 실패해도 뒷단계가 그 위에 계속 쌓인다.)
- **Good:** "`.claude/commands/quiz-daily.md`를 만들어서 다음 작업을 순서대로 수행하게 해 줘. 1. 퀴즈가 담겨 있는 파일의 구조를 읽고 이해하기 2. 현재 문제 개수와 분포 확인 3. 각 카테고리별로 부족한 부분 파악 4. 새 문제 추가 전 중복 체크 5. 문제 추가 후 형식 검증 6. 전체 데이터 백업 7. 실행 결과 상세 보고 **각 단계별로 검증하고, 실패하면 즉시 중단한 뒤, 오류를 보고해.**"
- **왜:** 다단계 위임의 진짜 위험은 실패가 아니라 **부분 성공 위에 계속 쌓이는 것**이다. 에이전트는 기본값이 "어떻게든 완주"라서 3단계가 어긋나도 4~7단계를 밀어붙이고, 손상이 마지막에 뭉쳐서 드러난다. 단계 사이에 검증 게이트 + 중단 조건을 문장으로 박으면 실패가 발생 지점에서 멈춘다. [[verification-loop]]가 *끝*에 붙는 합격 판정이라면 이건 *단계 사이*의 정지 조건이고, [[one-item-per-loop]]가 못 쓰는 "순서가 고정된 절차"에 적용된다.

## 역할 릴레이 파이프라인 (agent-relay-pipeline)
- **단계:** 구현위임
- **언제:** 서로 다른 관점의 점검(버그·성능·UX)이 다 필요한데, 한 에이전트에게 몰아주면 관점이 뭉개질 때.
- **Bad:** "코드 리뷰하고 성능도 개선하고 UX도 좋게 해줘." (한 컨텍스트에서 세 관점이 섞여 가장 만만한 것만 손댄다.)
- **Good:** 역할을 각각 한 문장으로 정의해 서브에이전트로 만들어 두고 — "코드 리뷰어: 코드를 읽고 버그는 없는지, 코딩 규칙에 따라 올바르게 작성되었는지를 점검하고 성능 최적화를 제안하는 전문 코드 품질 검토자." — **인계 순서를 프롬프트에 명시**한다: "`code-bug-analyzer`로 '냉장고를 부탁해' 애플리케이션 코드 전체를 리뷰한 뒤, 발견한 문제를 `performance-optimizer`가 수정해서 성능 최적화한 다음, `ux-design-advisor`가 사용자 경험을 개선하게 해 줘."
- **왜:** 관점마다 판단 기준이 충돌한다(성능 최적화 ↔ UX 추가). 한 컨텍스트에 섞으면 충돌이 은폐된 채 절충되지만, **앞 단계 산출물이 뒷 단계의 입력이 되는 릴레이**로 끊으면 각 단계가 자기 기준만 최대화하고 다음 단계가 그 결과를 명시적으로 뒤집는다. [[parallel-divergent-waves]]가 같은 스펙의 *병렬 발산*이라면 이건 다른 기준의 *순차 인계*다. [[senior-dev-review-pass]]·[[adversarial-review-subagent]]는 리뷰 1회로 끝나지만 여기선 리뷰→수정→개선이 한 위임에 물려 있다.
- **출처:** https://github.com/taehojo/vibecoding/blob/master/PROMPTS.md (07장)

## 모호성 표현을 감사 대상으로 명문화 (ambiguity-audit-rules)
- **단계:** 검증기
- **언제:** 에이전트가 만든 것이 코드가 아니라 **사실 콘텐츠·데이터**(문제은행·시드데이터·문서·카피)일 때. 컴파일도 테스트도 이 오류를 못 잡는다.
- **Bad:** "퀴즈 문제에 틀린 거 있으면 고쳐줘." (무엇이 틀린 건지 기준이 없어 에이전트가 자기 확신대로 넘어간다.)
- **Good:** 먼저 검증 규칙 문서를 만들어 프로젝트 메모리에 넣는다 — "퀴즈 문제 교차 검증 가이드라인 / 1. 정답이 하나뿐인가? 다른 해석 가능 시 조건 명시(예: 면적 기준, 2024년 기준) 2. 최상급 표현에 기준이 있는가? '가장 큰', '최초의' 등 표현에 측정 기준 명시 3. 시간과 범위가 명확한가? 변할 수 있는 정보는 시점 명시 4. 교차 검증했는가? 의심스러운 정보는 2개 이상 출처 확인" → 그다음 **소급 감사**: "지금까지 만들어진 문제를 방금 저장한 가이드라인을 참고해서 점검해 줘. 가이드라인에 맞지 않은 퀴즈와 정답이 있다면 이에 맞게 수정해줘." → 그리고 그 감사를 커맨드로 굳힌다: "'가장', '최초', '최대' 같은 최상급 표현이 있는지 찾아서 목록으로 보여줘."
- **왜:** 할루시네이션은 "거짓말"보다 **모호한 문장**으로 새어 나온다 — 기준 없는 최상급, 시점 없는 최신값. 이건 의미 판정이 아니라 **문자열 패턴 검출**로 바꿀 수 있고, 그 순간 기계적으로 감사 가능한 규칙이 된다. [[build-grader-first]]가 생성 *전*에 채점기를 세운다면 이건 이미 쌓인 자산에 규칙을 소급 적용하는 쪽이고, [[banned-words-for-sharpness]]가 문체용 금지어라면 이건 **사실성용 검출어**다.
- **출처:** https://github.com/taehojo/vibecoding/blob/master/PROMPTS.md (05-1, 05-2)

## 갈래별 메모리 분기 (per-variant-memory-split)
- **단계:** 컨텍스트주입
- **언제:** 한 프로젝트가 서로 규칙이 다른 갈래로 갈라질 때(웹/데스크톱, iOS/안드로이드, 서버/클라이언트).
- **Bad:** 루트 CLAUDE.md 하나에 양쪽 규칙을 다 적기 → 데스크톱 작업 중에 웹 규칙이 딸려 들어와 반응형 CSS가 얹힌다.
- **Good:** "손글씨 인식 프로그램을 웹 버전과 데스크톱 버전으로 나누어 개발하고 싶어. `web_version`과 `desktop_version` 폴더를 만들고, **각 폴더에 해당하는 CLAUDE.md 파일도 생성해 줘.**"
- **왜:** 프로젝트 메모리는 "많이 넣을수록 좋은 것"이 아니라 **작업 위치에 맞는 것만 걸려야 하는 것**이다. 한 파일에 상충하는 규칙이 공존하면 에이전트가 매번 어느 쪽을 적용할지 추측하고, 그 추측이 틀리면 조용한 오염으로 남는다. 디렉터리 = 규칙 스코프로 맞춰두면 위치가 곧 필터가 된다. [[persistent-context-file]]의 "상수를 고정한다"에 **"단, 갈래가 생기면 파일도 갈라라"**는 조건을 붙인 형태. [[context-hygiene]]의 공간축 버전.
- **출처:** https://github.com/taehojo/vibecoding/blob/master/PROMPTS.md (03-3)
