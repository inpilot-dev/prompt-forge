## 역인터뷰 (reverse-interview)
- **단계:** 킥오프
- **언제:** 맥락이 내 머리에만 있고 에이전트는 모를 때. 첫 프롬프트.
- **Bad:** "AX 해커톤 나가는데 뭐 만들면 좋을까? 아이디어 3개만 줘."
- **Good:** "이 글 읽고 필요한 정보 수집하고 내가 이제 해야 할 일 알려줘. 필요한 정보는 네가 나를 인터뷰해서 수집해."
- **왜:** 에이전트가 스스로 필요한 컨텍스트를 정의하게 함. 산출물을 바로 요구하면 뻔한 답만 나온다.
- **출처:** 실밸개발자 39분 §0 패턴①

## 원문 통째 복붙 (paste-full-source)
- **단계:** 킥오프
- **언제:** 과제문·룰·규격처럼 실격 조건이 디테일에 숨어 있는 자료를 넘길 때.
- **Bad:** 과제를 내가 요약해서 두세 줄로 전달.
- **Good:** "[과제 설명 / 제출물 구조(submission.zip) / 공식 문서 링크 / 로그 제출 룰 / 질문 5문항 / 심사 방식 / 마감일 전체 복붙]"
- **왜:** 요약하면 제출 규격·실격 조건 같은 디테일이 죽는다. 원문을 채점 루브릭으로 역산할 재료로 삼는다.
- **출처:** 실밸개발자 39분 §0 패턴②

## 조기 발산 차단 (block-early-divergence)
- **단계:** 컨텍스트주입
- **언제:** 에이전트가 컨텍스트도 없이 곧바로 리서치/생성을 돌리려 할 때.
- **Bad:** "좋아 이제 회사들 리서치해서 문제점 찾아줘."
- **Good:** "아직 리서치 돌리지 마. 이 정보 먼저 읽고 시작하자. [도메인 자료 복붙] 그 다음 뾰족한 니즈를 찾도록 리서치해."
- **왜:** 좋은 재료 없이 리서치하면 표면적·뻔한 결과. 순서는 스캐폴딩 → 컨텍스트 주입 → 리서치. "재료가 요리를 결정한다."
- **출처:** 실밸개발자 39분 §1 패턴③

## 인터뷰 상시 개방 (interview-always-open)
- **단계:** 컨텍스트주입
- **언제:** 위임 프롬프트 끝에 항상. 내가 미처 못 준 정보가 있을 때 에이전트가 멈추지 않게.
- **Bad:** 지시만 주고 "알아서 해" — 부족하면 혼자 추측으로 채운다.
- **Good:** "…후보 문제 3개씩 뽑아봐. 더 필요한 정보 있으면 물어봐줘."
- **왜:** 에이전트가 빈 정보를 추측으로 메우는 대신 되묻게 한다. 역인터뷰의 상시판.
- **출처:** 실밸개발자 39분 §1 패턴⑥

## 산출물 구조 지정 (structured-output-spec)
- **단계:** 리서치위임
- **언제:** 위임 결과물의 형태(폴더/파일/섹션/필드)를 사전에 못 박아야 할 때.
- **Bad:** "문제점 찾아줘." — 산출물 형태 미정, 회사마다 품질 들쭉날쭉.
- **Good:** "산출물: pain point 목록(각 근거 링크) / 후보 문제 3개 — 각각 {문제 정의 한 문장·공개 근거 URL 2개+·솔루션 스케치·정렬도·구현 가능성} / 추천 1순위와 이유. 회사별 폴더에 정리."
- **왜:** 형태를 미리 규정하면 병렬 위임 결과가 균질해지고 바로 다음 단계 입력으로 쓸 수 있다.
- **출처:** 실밸개발자 39분 §2 패턴④

## 프롬프트 파일화·템플릿화 (prompt-as-file-template)
- **단계:** 리서치위임
- **언제:** 같은 작업을 여러 대상(회사·모듈)에 병렬로 돌리거나 재사용할 때.
- **Bad:** "카카오페이증권 문제점 찾아줘. 그리고 무신사도. 그리고…" (채팅창에 매번 새로 침)
- **Good:** "`PROMPT.md`로 만든다 — [컨텍스트 / 리서치 지침 / 산출물 / 품질 기준]은 공통, '이 기업 특화 탐색 각도' 섹션만 회사별 교체."
- **왜:** 즉흥 채팅은 재사용 불가·품질 편차. 공통 구조 + 교체 슬롯 → N개 병렬 + 다음 프로젝트 자산.
- **출처:** 실밸개발자 39분 §2 패턴⑦

## 금지어로 뾰족함 강제 (banned-words-for-sharpness)
- **단계:** 리서치위임
- **언제:** 에이전트가 넓고 뻔한 답으로 도망갈 위험이 있을 때.
- **Bad:** "좋은 문제 찾아줘." — "CS 자동화", "업무 효율화" 같은 답이 나온다.
- **Good:** "넓고 뻔한 문제('CS 자동화','업무 효율화') 금지 — 구체적 상황·데이터가 보이는 문제로. 모든 주장에 URL을 달 것."
- **왜:** 뻔한 답을 명시적으로 차단하면 탐색이 구체·근거 쪽으로 밀린다.
- **출처:** 실밸개발자 39분 §2 패턴⑧

## 심사자 취향 명시 (judge-taste-explicit)
- **단계:** PRD
- **언제:** 결과물을 평가할 주체의 취향/편향이 결과 형태를 좌우할 때.
- **Bad:** "PRD 써줘." — 평가자 관점이 빠져 형태가 임의로 결정됨.
- **Good:** "사람이 평가하니 눈에 보이는(visually appealing) 결과물이 유리하다 — 데모 형태를 명시해. 비주얼한 솔루션을 줄 수 있는 문제가 좋다."
- **왜:** 심사자 취향을 컨텍스트로 주입하면 산출물이 평가 축에 정렬된다.
- **출처:** 실밸개발자 39분 §3 패턴⑤

## 수미상관 반복 점검 (coherence-recheck)
- **단계:** PRD
- **언제:** 문제 정의와 솔루션이 논리적으로 이어지는지 검증이 필요할 때.
- **Bad:** 문제 정하고 곧바로 솔루션으로 넘어감 — 연결 검증 없음.
- **Good:** "문제 ↔ 솔루션의 논리적 수미상관이 최우선 평가 기준이다. 그게 맞는지 다시 봐. 다 풀지 말고 내가 가장 잘 풀 수 있는 문제 하나로 우선순위를 정해라."
- **왜:** 문제-솔루션 정합성이 심사 1급 기준. "다 하기"는 좋은 솔루션이 아니다 — 하나로 좁힌다.
- **출처:** 실밸개발자 39분 §3 패턴⑫ + 라이브(Solution Prioritization)

## 스코핑 재보정 (scoping-recalibration)
- **단계:** 스코핑
- **언제:** 에이전트가 뽑은 문제/작업이 사람 기준으로 작게 스코핑됐을 때.
- **Bad:** "음 이 정도면 될 것 같은데. 그냥 이걸로 진행해."
- **Good:** "사람이 3~4주 걸릴 규모로 스코핑해 달라. 그거를 에이전트로 1~2일 만에 끝낸다. 솔루션이 너무 간단하면 안 된다. (스코핑 커도 된다, 한 달 넘어가도 된다.)"
- **왜:** 에이전트는 사람 기준으로 작게 스코핑한다. "사람 N주 = 에이전트 1~2일"로 눈금을 명시적으로 다시 잡는다.
- **출처:** 실밸개발자 39분 §4 패턴⑨ + 라이브(scalable·impactful)

## 최종 순간 시뮬레이션 (final-moment-simulation)
- **단계:** 솔루션깎기
- **언제:** 솔루션을 심사자 관점에서 날카롭게 다듬는 마지막 리뷰.
- **Bad:** "솔루션 좀 더 좋게 개선해줘." — "좋게"의 기준이 없음.
- **Good:** "심사자는 아마 agent한테 이 plugin 써보라고 시킬 거야. 그 순간 결과가 어떻게 나와야 1등 할지 역산해서 solution을 깎아 문제를 sharp하게 관통하게 만들어."
- **왜:** 결과가 소비되는 실제 최종 순간(3분)에서 역산하면 개선 방향이 구체화된다.
- **출처:** 실밸개발자 39분 §5 패턴⑩

## 기준 상향 언어 (bar-raising-language)
- **단계:** 솔루션깎기
- **언제:** 에이전트의 목표 눈높이를 말로 계속 끌어올려야 할 때.
- **Bad:** "적당히 잘 만들어줘."
- **Good:** "5,000명 중 1등 할지, 심사자(사람+AI) 둘 다 만장일치할지, 하나의 부서가 될 만한·오늘 당장 쓸 수 있는·visually appealing and unique and impactful 하게 다시 검토해."
- **왜:** 점수 기준을 상향 언어로 계속 끌어올리면 산출물 목표치가 따라 올라간다.
- **출처:** 실밸개발자 39분 §5 패턴⑪

## 채점기 선제작 (build-grader-first)
- **단계:** 검증기
- **언제:** 산출물을 만들기 전에 "무엇으로 채점할지"부터 정해야 할 때.
- **Bad:** "다 만들고 나서 잘 됐는지 봐줘." — 사후 평가, 기준 없어 재작업 폭증.
- **Good:** "AI가 어떻게 리뷰할지, 사람이 어떻게 리뷰할지 reverse engineer 해서 리뷰 rubric을 각각 만들고 그걸 스킬로 굳혀라. 매 stage commit마다 돌려 점수 매기고, 잘 나올 때까지 개선. 바는 실제보다 의도적으로 높게."
- **왜:** 평가 체계를 먼저 역설계해 스킬로 고정. "높은 기준에서 높은 점수 > 낮은 기준에서 높은 점수."
- **출처:** 실밸개발자 39분 §6 패턴⑬

## 자가수렴 루프 위임 (self-converging-loop-delegation)
- **단계:** 구현위임
- **언제:** 스펙이 확정돼 구현을 통째로 위임하고 손을 뗄 때.
- **Bad:** "이제 코드 짜줘. 다 되면 알려줘." — 종료 조건·검증 관점 없음.
- **Good:** "HANDOFF.md 읽고 구현 시작. subagent orchestration으로 구현하고, 검증 통과·만점 나올 때까지 계속 루프 돌려. ai judge / human judge 스킬 써야 하면 써. 통과할 때까지 루프 돌고 다 끝나면 보고."
- **왜:** 종료 조건을 "만점"으로 걸고 통째로 위임 → 자가수렴. 그동안 사람은 손을 뗀다.
- **출처:** 실밸개발자 39분 §7 패턴⑭

## 투웨이 검증 (two-way-validation)
- **단계:** 구현위임
- **언제:** 산출물의 소비자가 사람과 에이전트 양쪽일 때.
- **Bad:** "사람이 보기 좋게만 만들어줘." (또는 에이전트만 고려)
- **Good:** "검증은 무조건 two-way: 사람(결과 보고 결정할 stakeholder) + Agent(플러그인을 부릴 주체) 두 관점에서 만점 나올 때까지."
- **왜:** 소비자를 사람+에이전트 둘로 정의하면 한쪽에만 최적화된 결과를 막는다.
- **출처:** 실밸개발자 39분 §7 패턴⑮

## 실데이터 강제 (real-data-enforcement)
- **단계:** 구현위임
- **언제:** 데모 데이터로 대충 통과할 위험이 있는 구현/테스트를 위임할 때.
- **Bad:** 데모/목 데이터로 테스트해 "통과"로 처리.
- **Good:** "기능 고장 절대 금지. 테스트는 데모 데이터 말고 실제 API·MCP 기반으로. 실데이터로 서브에이전트 각각 돌려 산출물 보고."
- **왜:** 데모 데이터는 실패를 숨긴다. 실제 API/MCP로 강제하면 진짜 동작 여부가 드러난다.
- **출처:** 실밸개발자 39분 §7 패턴⑯

## 평가 기준 자체를 업데이트 (update-the-rubric-itself)
- **단계:** 검증루프
- **언제:** 결과가 약해 고치고 싶은데, 같은 실수가 반복될 때.
- **Bad:** "음 이거 별론데. 색깔 좀 바꾸고 더 예쁘게 해줘." — 일회성 수정, 기준은 그대로.
- **Good:** "지금 결과가 왜 약한지 평가하고, 그 발견을 반영해 너의 평가 기준(rubric) 자체를 업데이트해라. 업데이트된 기준으로 다시 채점하고 만족할 때까지 refine → 재채점 루프. 나는 마지막에 눈으로 검증한다."
- **왜:** "그냥 바꿔줘"가 아니라 "기준을 바꿔라". 내 검증 시스템과 에이전트의 검증 시스템을 일치시키면 알아서 반복한다. 첫인상·직관만 마지막에 사람이 잡는다.
- **출처:** 실밸개발자 39분 §8 + 라이브(가장 강조)

## 세션 재-온보딩 (session-reonboarding)
- **단계:** 컨텍스트주입
- **언제:** 세션이 바뀌어 에이전트가 이전 맥락을 잃은 채로 이어서 작업할 때. 매 세션 첫 프롬프트.
- **Bad:** (새 세션에서 바로) "이어서 공유 기능 만들어줘."
- **Good:** "initialize.md부터 읽고, 프로젝트 구조를 이해한 다음 로그인 기능부터 만들어줘."
- **왜:** 세션이 끊기면 에이전트의 작업 기억도 끊긴다. 매 세션을 "문서부터 다시 읽기"로 열면 맥락이 복원된 상태에서 시작한다. 기억은 대화창이 아니라 파일에 둔다.
- **출처:** 커리어해커 알렉스 — High Output Club '실리콘밸리 개발자처럼 바이브코딩하는 법' https://blog.highoutputclub.com/vibecoding-with-ai-replit-careerhackeralex/

## 프로젝트 상수 메모리화 (persistent-context-file)
- **단계:** 컨텍스트주입
- **언제:** 브랜드 규칙·톤·컨벤션처럼 매번 똑같이 반복되는 제약을 프롬프트마다 다시 설명하게 될 때.
- **Bad:** 매 프롬프트마다 "브랜드 컬러는 파란색이고 폰트는 Pretendard고 톤은 친근하게…" 반복.
- **Good:** "CLAUDE.md에 기록해줘 — 브랜드 컬러 #2E75B6 / 폰트 Pretendard / 톤은 친근하고 전문적인 해요체."
- **왜:** 반복 제약을 프롬프트에 넣으면 세션마다 새고 편차가 난다. 프로젝트 메모리 파일(CLAUDE.md)에 고정하면 모든 세션이 같은 규칙 위에서 돈다. [[prompt-as-file-template]]이 '교체 슬롯'이라면 이건 '고정 상수'다.
- **출처:** 커리어해커 알렉스 — High Output Club '2026 클로드 코드 사용법' https://blog.highoutputclub.com/2026-claude-code-for-non-developers/

## 회귀 델타 디버깅 (regression-delta-debug)
- **단계:** 검증루프
- **언제:** 방금 전까지 되던 게 특정 변경 이후 깨졌을 때. 디버깅 프롬프트.
- **Bad:** "이미지가 안 나와. 고쳐줘."
- **Good:** "이전까지는 결과 페이지가 잘 나왔어. 그런데 공유 버튼을 추가한 이후, 이미지가 안 나와."
- **왜:** "언제부터 / 무엇을 바꾼 뒤"라는 경계를 주면 원인 탐색이 그 변경 구간으로 좁혀진다. "고쳐줘"는 전수조사를 시켜 시간을 태운다.
- **출처:** 커리어해커 알렉스 — High Output Club '실리콘밸리 개발자처럼 바이브코딩하는 법' https://blog.highoutputclub.com/vibecoding-with-ai-replit-careerhackeralex/

## 작동 스냅샷·롤백 (checkpoint-rollback)
- **단계:** 구현위임
- **언제:** 기능을 계속 얹어가며 만들 때. 다음 단계로 넘어가기 직전.
- **Bad:** 위에 계속 얹어 고치다가 전부 깨지면 되돌릴 지점이 없다.
- **Good:** "여기까지 정상 작동 확인했어. 스냅샷 저장하고 다음 기능으로 가자. 문제 생기면 이 지점으로 롤백."
- **왜:** 정상 상태마다 체크포인트를 남기면 실패해도 마지막 정상 지점으로 즉시 복귀한다. 되돌릴 곳이 있으면 무한 디버깅 루프에 빠지지 않는다.
- **출처:** 커리어해커 알렉스 — High Output Club '실리콘밸리 개발자처럼 바이브코딩하는 법' https://blog.highoutputclub.com/vibecoding-with-ai-replit-careerhackeralex/

## 레퍼런스로 스타일 학습 (learn-from-reference)
- **단계:** 리서치위임
- **언제:** "내 톤/스타일로"처럼 형용사로만 존재하는 기준을 결과물에 재현시켜야 할 때.
- **Bad:** "내 톤으로 뉴스레터 써줘." — '내 톤'의 실체를 안 준다.
- **Good:** "좋아하는 에세이 모음으로 구성법을 학습하고, 제 톤앤매너를 참고해서 새 에세이의 구조를 만들어줘." (레퍼런스 파일 첨부)
- **왜:** 추상적 형용사 대신 실제 샘플을 재료로 주면 에이전트가 패턴을 역추출해 재현한다. few-shot을 파일로 넘기는 것.

## 멀티채널 팬아웃 변환 (multichannel-fanout)
- **단계:** 구현위임
- **언제:** 하나의 소스를 여러 채널 포맷으로 동시에 재가공할 때.
- **Bad:** "이 글 여기저기 올리게 바꿔줘." (또는 채널마다 따로따로 요청)
- **Good:** "이 뉴스레터를 링크드인, 오픈채팅방 홍보글, 인스타 카드뉴스, 스레드 글로 각각 변환해줘."
- **왜:** 목적지 채널을 목록으로 못 박으면 톤·길이·형식이 채널별로 분기된다. "여기저기"는 뭉뚱그린 결과를, 채널 명시는 채널맞춤 결과를 만든다.
