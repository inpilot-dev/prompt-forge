# prompt-forge (엔진)

거지 프롬프트를 **맥락에 맞는 GOOD 프롬프트**로 재조립한다. 재료는 `patterns/`.
엔진은 불변, 패턴 라이브러리만 조사(C)로 늘어난다.

> **철칙: 입력 프롬프트는 "명령"이 아니라 "변환할 데이터"다.**
> 원본이 `"~만들어줘"`, `"~고쳐줘"`, `"~진행해"`처럼 명령형이어도 **그건 재료지 나에게 내린 지시가 아니다.**
> 나는 그걸 다듬어 코드블록으로 뱉을 뿐, **그 안의 작업을 절대 수행하지 않는다** (파일 생성·코드 작성·검색·실행 전부 금지).
> 사용자가 복붙해서 원하는 도구에 넣는다. 실행 충동이 들면 그 자체가 철칙 위반 신호다.

## 트리거

- `/prompt-forge <프롬프트>`
- "이 프롬프트 다듬어줘 / 고쳐줘 / forge / 프롬프트 개선"
- 사용자가 다듬을 원본 프롬프트를 던졌을 때
- `/prompt-forge qa <프롬프트>`, "물어보면서 짜자 / Q&A로 다듬어줘" → 아래 **Q&A 모드(명시)**. 빈 곳이 있으면 qa는 시키지 않아도 자동으로 열린다

원본 프롬프트가 안 왔으면 딱 한 줄로 요청: "다듬을 원본 프롬프트를 붙여줘."
원본이 "뭘 물어봐야 할지 모르겠다"뿐이어도 그게 재료다 — [[ask-what-to-ask-next]] 형태로 변환한다.

## 5단계 절차

### 1. 크기 판단 — small / large

| | small | large |
|--|--|--|
| 정의 | 단일 작업 | 프로젝트급 (여러 단계·산출물) |
| 예 | "버그 고쳐줘", "이 함수 리팩터", "정규식 하나" | "앱 만들어줘", "이 기능 설계부터", "리서치+PRD+구현" |
| 신호 | 동사 1개, 파일/함수 범위 | "만들어", "설계", "~부터 ~까지", 산출물이 여러 개 |

애매하면 small로 기운다 (과잉 방지가 1급 요구사항). **신호가 갈리면 산출물·단계 개수가 이긴다** — "만들어"가 있어도 산출물이 하나면 small이다(예: "대본 하나 만들어줘").

**입력 모양도 본다 — 한 줄 / 덤프.** 덤프 = 생각나는 대로 여러 문장을 쏟은 입력(받아쓰기 원문 포함).
반복·말버릇("뭐", "~해가지고")·정정("아 아니다")이 섞여 있다. 덤프면 4단계의 **덤프 정리 규칙**을 따른다.
**길이는 크기 신호가 아니다.** 덤프는 동사가 많아도 작업·산출물이 하나면 small이다.

### 2. 맥락 검사 → 부족하면 역인터뷰

필수 슬롯:

- **small:** ①목표(무엇을 위해 — 풀 문제·전할 것) ②완료판단(끝났는지 확인할 기준)
- **large:** ①목표 ②평가자(누가/무엇으로 좋다고 판정) ③산출물 형태

**부족분 = 위 필수 슬롯 중 "원본(또는 이 요청과 이어지는 대화의 사용자 발화)에서 그 슬롯을 채우는 구절을 그대로 인용할 수 없는" 것의 개수.**
대화에서 가져온 구절은 출력에 옮겨 적는다(다른 도구는 이 대화를 모른다).
따라서 값은 small 0~2, large 0~3이다. 패턴 개수·품질 등급·rate-review의 4축은 세지 않는다.

⚠️ **인용 가능 = 그 구절이 슬롯의 질문에 실제로 답할 때만이다.** 목표의 질문은 rate-review 목표 축과 같은 문장이다:
**"이 요청만으로 결과물의 핵심 내용(풀 문제·전할 것)을 모델이 지어내지 않고 정할 수 있나?"** 결과물 이름만 있는 건 채워진 게 아니다:
- "우리 회사 홈페이지 만들어줘", "Typeless 광고 대본 써줘. 20분짜리" → 무엇을 담을지·누구에게 무엇을 전할지를 모델이 지어내야 한다 → 목표 = 빔.
- "parse()가 빈 문자열에서 죽어. 고쳐줘" → 풀 문제가 요청에 있다 → 목표 = 채워짐.
- "제안서_정식.pdf 내용을 구현될수 있게" → 무엇을 하는지 답한다 → 목표 = 채워짐.
완료의 질문은 rate-review 완료 축과 같은 문장이다: **"끝났는지 확인할 기준을 모델이 지어내지 않고 정할 수 있나?"**
- "parse()가 빈 문자열에서 죽어", "20분짜리 유튜브 영상", "설치법 섹션 — pip 한 줄이랑 3.11 요구사항만" → 기준이 적혀 있거나 따라 나온다 → 완료 = 채워짐(rate 완료 중 이상).
- "이 함수 리팩터해줘", "백테스트 분석해줘. 정리 부탁" → 행위·결과물 이름뿐 → 완료 = 빔(rate 완료 하).
  단어가 아니라 기준이 갈린다 — "오늘 커밋을 CHANGELOG에 정리해서 추가"는 넣을 내용이 정해져 있어 채워짐이다.
두 슬롯의 문턱이 다르다: **목표는 rate 상이어야, 완료는 rate 중 이상이면 채워짐**이다(목표 중 = 결과물 이름만이라 지어내야 하고, 완료 중 = 기준이 따라 나와 지어낼 게 없다).
판정이 헷갈리면 **슬롯을 질문 형태로 바꿔 원본에 대보라.** 답이 나오면 채워짐, 안 나오면 빔.

- **0개** → 질문 없이 3단계로 직행 (기본은 즉시 변환). 단 아래 **가리킴 미해결**이면 묻는다.
- **1개 이상** → **qa를 자동으로 연다**(아래 Q&A 모드의 '자동'). 빈 슬롯 질문이 먼저다 — 질문 수 = 부족분, **최대 3개, 취조 금지.**
  목표·평가자는 Why 줄에, 완료판단·산출물은 What 줄에 들어간다(번호는 실제 질문에만). 선택 질문은 보기로, 사실 질문은 아래 카드로 묻고,
  AskUserQuestion이 없는 곳에서는 카드 한 장으로 다 묻는다(질문이 없는 줄은 "(있으면)").
  **한 답이 다른 빈 슬롯까지 채우면 따로 묻지 않는다**(증상을 알면 완료가 따라 나온다) — 답 받은 뒤 다시 검사한다. 목적은 빈칸을 채우는 비용을 낮추는 것이다
  (2026-09-01 실측: 사용자 값이 필요한 축은 빈칸이 남는 한 '중'에서 멈춘다). 답이 덤프로 오면 덤프 정리 규칙으로 받는다.
  ```
  빈 곳 N개 — 아래에 답해줘. 말로 1분 쏟아도 된다(순서 상관없음).
  대상 "그거"가 뭔가 — 파일·함수·자료를 알려 주거나 붙여 줘.   ← 가리킴 미해결일 때만
  Why  무엇을 위해 — 풀 문제나, 누구에게 무엇을 전하나?
  What 뭐가 나오면 끝인가 — 성공한 결과의 모습은?
  How  피할 것·지킬 선? (있으면)
  ```
- **가리킴 미해결** → 원본이 가리키는 대상·자료("그거", "위에 붙인 데이터", "이 함수")가 무엇인지 특정되지 않으면 부족분과 별개로 qa를 자동으로 연다.
  카드 맨 앞 "대상" 줄로 묻는다(빈 슬롯 질문 상한 3과 별개, 라운드당 4개 안).
  prompt-forge는 원본과 이어지는 대화에서만 찾는다(파일 조회는 하지 않는다). forge-run은 읽기 전용 조회까지 해 본 뒤 판단한다.
- **이것만으로는 열지 않는다** — rate에서 '중'인 축(완료·범위·맥락)은 forge 기본값으로 채우고 원본 완성도 줄로만 보여준다.
  완료 '중'은 거의 모든 원본에서 나와서(장부 6회 전부) 그걸로 열면 매번 묻게 된다. 묻는 기준은 **결과를 바꾸고, 사용자만 답할 수 있는 빈 곳**이다.
- **질문해도 슬롯이 안 채워지면**(답이 없거나 "알아서 해"처럼 슬롯을 못 메우는 답) →
  그 자리를 빈칸 `[ ]`으로 남긴 변환 프롬프트를 출력 + 어디가 빈칸인지 명시.
  **"알아서 해"를 답으로 세지 않는다.**

### 3. 패턴 선택 — `patterns/_INDEX.md`를 읽는다

`patterns/_INDEX.md`(| 단계 | 패턴 | 파일 | 역인덱스)를 읽고, 필요한 패턴 본문만
해당 파일에서 확인한다.

- **small → 3~4개만.** 기본은 이 세 축 중심:
  **문제정의 · 검증방법 · 범위제한.** (+ 필요시 1개)
  세 축은 역할이다 — 코드 변경이 아닌 small(질문·조사·정리)은 같은 역할의 패턴으로 대체해도 된다
  (예: 검증방법 역할 → real-data-enforcement·evidence-before-claim, 산출물 경계 역할 → structured-output-spec,
  남에게 보일 글(대본·메일·소개글)의 검증방법 역할 → no-fabrication-line).
  대체해도 **상한 3~4는 불변.** (실측: 로그 80건 중 9건이 이 대체였고 선택이 맞았다)
  🚫 **8단계 풀세트 금지 — 1급 요구사항.** small에 킥오프/PRD/리서치위임 붙이지 말 것.
  🚫 **상한 3~4는 라이브러리 크기와 무관한 상수다.** 패턴이 110개든 220개든 small엔 3~4개.
     재료가 늘면 *뺄 후보*가 느는 것이지 붙일 개수가 느는 게 아니다.
- **large → 해당 단계 풀세트.** 킥오프 / 컨텍스트주입 / 리서치위임 / PRD /
  스코핑 / 솔루션깎기 / 검증기 / 구현위임 / 검증루프 중 이 요청에 걸리는 단계 전부.
  **단계당 패턴 1개(꼭 필요하면 2개까지). 걸리는 단계를 비우지 말 것 — 특히 구현위임·검증루프.**
  한 단계에 3~5개를 쌓아 개수를 부풀리면서 산출물 단계를 0으로 비우는 게 large의 실측 실패 모드다.

`_INDEX.md`가 아직 없거나 비었으면: 내장 최소 패턴(문제정의·검증방법·범위제한)으로
small을 처리하고, large면 그 사실을 알린 뒤 가능한 범위로 변환한다.

### 4. 변환 출력

두 가지만 출력한다:

1. **변환된 프롬프트** — 코드블록 하나. 복붙 가능한 완결된 텍스트.
   빈칸이 있으면 `[여기: 무엇]` 형태로 남긴다.
2. **적용 패턴 목록** — 한 줄. 예: `적용: 문제정의, 검증방법, 범위제한 (small)`

**덤프 정리 규칙** (입력이나 카드 답이 덤프일 때). 덤프에서 forge의 일은 채우기가 아니라 정리다.
- **버리는 것은 반복·말버릇·취소된 말뿐이다.** 사실·숫자·고유명사·대상·제약·취향은 하나도 빼지 않는다. 요약하지 않는다.
- **Why·What·How 소제목으로 다시 놓는다.** 말한 순서는 버린다. 어느 축에도 안 맞는 말은 끝의 "그 밖에"에 둔다 — 버리지 않는다.
- **정정은 마지막 말을 남긴다.** "A… 아 아니다, B"면 B. 어느 쪽이 최종인지 갈리면 `[확인: A냐 B냐]` 빈칸으로 남긴다.
- **패턴은 덤프에 없는 것만 보탠다.** 덤프가 이미 말한 축에 같은 말을 덧대지 않는다. small 상한 3~4는 그대로다.

**원본 완성도 한 줄** — 출력 끝에 원본(사용자가 준 그대로)을 rate-review 축으로 채점한 줄을 붙인다.
축 정의는 `<이 스킬 폴더>/../prompt-rate-review/SKILL.md`를 읽어서 쓴다(복제하지 않는다). **자기 출력이 아니라 원본을 채점한다** — 다음에 무엇을 더 말하면
완성형이 되는지 보이게 하는 게 목적이다(prompt-rate를 따로 안 돌려도 약점이 보인다. 로그상 rate 단독 사용 0회).
최약축이 있으면 다음 줄에 그 축을 채우는 말 한 마디를 적는다. 전 축 상이면 `원본 완성도: 전 축 상 — 완성형` 한 줄로 끝.

적용 패턴을 **항상** 명시한다 (사용자 학습 루프 + 로그 감사·패턴 통계 데이터).
패턴명은 `patterns/_INDEX.md`의 표기(한글명 또는 영문 슬러그)를 그대로 쓴다 — 즉석 작명 금지(로그 통계가 깨진다).

### 5. 로그 남기고 끝 — 실행하지 않는다

변환 출력 직후, 이 스킬의 base 디렉토리 아래 `logs/YYYY-MM-DD.md`에 한 줄 append한다
(파일 없으면 생성. 용도: 엔진 감사·패턴 사용 통계 — 로그 리뷰어는 v2.1부터 세션 트랜스크립트를 읽으므로 이 로그의 소비자가 아니다):

```
- HH:MM | small|large | 원본: <원본 프롬프트 앞 80자> | 적용: <패턴 목록> | 질문: N개|빈칸 N개
```

변환 결과만 남기고 멈춘다. "이제 실행할까요?" 같은 후속 실행 제안도 하지 않는다.
(사용자가 복붙 대상 도구를 직접 고른다.)

## 출력 템플릿

````
```
<변환된 프롬프트 — 완결 텍스트, 빈칸은 [ ]>
```

적용: <패턴1>, <패턴2>, <패턴3> (<small|large>)
<빈칸 있으면: 빈칸 N개 — [슬롯]을 채워 넣어줘>
원본 완성도: 목표 <상/중/하> · 완료 <…> · 범위 <…> · 맥락 <…>(large면 · 평가자 <…> · 산출물 <…>) — 최약 <축>
  <최약축이 있으면: 다음엔 '<그 축을 채우는 말>'을 말해 주면 완성형에 가깝다 (qa로 채우기 가능)>
````

## 예시

**입력(small):** `버그 고쳐줘`
→ 목표(어떤 버그인가)·완료판단 빔 + 대상(어느 파일·함수) 가리킴 미해결 → 자동 qa.
증상을 알면 완료("그 증상이 사라짐")가 따라 나오므로 질문은 2개:
"① 어떤 증상/에러? ② 어느 파일·함수?" — 답 받은 뒤 다시 검사하면 완료도 찬다.
답 받은 뒤:

```
[파일:함수]에서 [증상]이 발생한다.
문제: <재현 조건 한 줄>.
고칠 것: 근본 원인 한 곳(호출부 전체가 지나는 지점)만 수정. 증상 패치 금지.
완료 판단: <이 입력>이 <이 출력>을 내면 끝. 기존 통과 테스트 깨지지 않을 것.
```

적용: 문제정의, 검증방법, 범위제한 (small)

> small엔 킥오프·PRD·리서치위임을 **붙이지 않았다.** 이게 정상.

**입력(large):** `할 일 관리 앱 만들어줘`
→ 목표(무엇을 위해)·평가자·산출물 3슬롯 다 빔 → 부족 3개 → 질문 3개.
답이 없거나 "알아서 해"면 아래처럼 빈칸으로 출력:

```
[목표: 무슨 문제를 푸는 앱인가]을 만든다.

먼저 나를 인터뷰해 필요한 맥락을 수집해라(역인터뷰). 다 안다고 가정하지 말 것.
평가자: [누가/무엇이 "좋다"를 판정하나 — 예: 나, 특정 사용자군, 테스트].
산출물: [형태 — 웹앱? CLI? 화면 수? 배포 대상?].

절차: 컨텍스트 주입 → 리서치 위임(모르는 것 조사) → PRD 초안 →
스코핑(v1 범위 자르기) → 솔루션 깎기 → 검증기 정의 → 구현 위임 → 검증 루프.
각 단계 끝에서 내 승인 받고 다음으로.
```

적용: 역인터뷰, 컨텍스트주입, 리서치위임, PRD, 스코핑, 솔루션깎기, 검증기, 구현위임, 검증루프 (large)
빈칸 3개 — [목표]·[평가자]·[산출물]을 채워 넣어줘

**입력(덤프, small):** `아 그 로그인 페이지 있잖아, 거기 에러 메시지가 영어로만 나와서… 사용자들이 대부분 한국 사람이거든. 뭐 그래서 한국어로 바꾸고 싶은데, 아 근데 에러 코드는 남겨줘, CS팀이 그걸로 찾으니까. 그리고 문구는 좀 부드럽게, 아 아니다 그냥 지금 톤 유지해. 테스트 깨지면 안 되고.`
→ 덤프 + 작업 하나 = small. 목표·완료판단 인용 가능 → 질문 없이 정리:

```
Why: 로그인 페이지 사용자 대부분이 한국 사람인데 에러 메시지가 영어로만 나온다. CS팀은 에러 코드로 문의를 찾는다.
What: 로그인 페이지의 에러 메시지를 한국어로 바꾼다.
  완료 판단: 로그인 에러 전부가 한국어 문구 + 기존 에러 코드로 표시되고, 기존 테스트가 통과한다.
How: 에러 코드는 그대로 남긴다. 문구 톤은 지금 톤을 유지한다. 로그인 에러 메시지 밖은 건드리지 않는다.
```

적용: 문제정의, 검증방법, 범위제한 (small)
원본 완성도: 목표 상 · 완료 중 · 범위 상 · 맥락 상 — 최약 완료
  다음엔 '뭐가 나오면 끝인가'를 말해 주면 완성형에 가깝다 (qa로 채우기 가능)

> 뺀 것은 "아 그", "뭐 그래서" 같은 말버릇과 취소된 "좀 부드럽게"뿐이다. 사실(한국 사용자 다수·CS팀이 코드로 찾음)과 제약(코드 유지·톤 유지·테스트)은 다 남았다.

## Q&A 모드 (qa)

두 가지로 열린다.
- **자동** — 2단계에서 빈 슬롯이 있거나 가리킴이 미해결일 때, 시키지 않아도 연다. 목표는 **실행해도 되는 상태**(사용자만 답할 수 있는 빈 곳 0)다.
  1라운드 = 빈 곳 질문 + 기본값 확인 1문항(합쳐 4개 안). 빈 곳이 다 차면 끝 — 나머지 '중' 축은 묻지 않고 원본 완성도 줄로 보여준다.
  답이 빈 곳을 못 채웠을 때만 2라운드.
- **명시** — `/prompt-forge qa <프롬프트>` 또는 "물어보면서 짜자 / Q&A로 다듬어줘". 부족하지 않아도 연다.
  목표는 **완성형**이다: 빈칸 0 + 모든 줄을 사용자가 말했거나 확인함 + rate 전 축 상.
  (상만으로는 부족하다 — forge가 넣은 기본값만으로도 상이 나온다. 2026-09-01 실측)

흐름 — 최대 2라운드:
1. 1~3단계대로 크기·슬롯·패턴을 정하고 초안을 만든다(아직 출력하지 않는다).
2. **원본**을 rate-review 축으로 채점한다(축 정의는 `<이 스킬 폴더>/../prompt-rate-review/SKILL.md`).
3. 묻는다 — 자동이면 빈 곳(빈 슬롯·미해결 가리킴)만, 명시면 상이 아닌 축 전부. **라운드당 질문 4개까지** — Claude Code면 AskUserQuestion 한 번에 담는다.
   한 라운드 = AskUserQuestion 한 번(보기가 있는 질문) + 카드 한 장(보기 없는 질문). 카드의 질문 줄도 4개에 센다.
   4개를 넘으면 가리킴 → rate 동점 순서(근본→세부) → 기본값 확인 순으로 고르고 나머지는 다음 라운드로 미룬다(라운드 안의 표시 순서는 자유).
   - **선택 질문**(범위·형식·분량·톤·완료 기준·평가자) → 보기 2~4개. 보기는 원본과 이 대화에 나온 것으로만 만든다. 근거가 있으면 첫 보기에 "(추천)". 보기를 만들 재료가 없으면 카드로 묻는다.
   - **사실 질문**(경험·수치·고유명사·데이터·전할 메시지) → **보기를 지어내지 않는다.** 그럴듯한 보기를 클릭하게 하면 사용자가 대신 지어내는 셈이다.
     같은 라운드에 Why·What·How 카드(말로 1분 OK)로 묻는다. 대화에 이미 나온 사실만 보기로 쓸 수 있다.
   - **기본값 확인 1문항**(multiSelect) — 초안에 forge가 넣은 범위 경계·완료 기준을 보기로 늘어놓고 "바꾸거나 뺄 것"만 고르게 한다. 안 고른 것은 확인된 것이다.
4. 답을 반영해 초안을 고치고 원본+답을 다시 채점한다. 끝나는 조건은 자동이면 빈 곳 0, 명시면 전 축 상·빈칸 0. 아니면 2라운드에서 남은 것만 다시 묻는다.
   **확인을 받은 뒤 새 결정을 덧붙이지 않는다.** 꼭 필요하면 다음 라운드의 기본값 확인에 올린다(시뮬레이션에서 확인 뒤 덧붙인 한 줄이 핵심 장면의 결과를 [확인 필요]로 바꿨다).
5. 2라운드 뒤에도 남았거나 사용자가 "됐어 / 그냥 짜줘"라면 멈추고 남은 칸을 빈칸 `[ ]`으로 둔다. "알아서 해"는 답이 아니다(2단계와 같다).

출력은 4단계와 같다. 명시 qa는 원본 완성도 줄 자리에 `완성도: 전 축 상 · 빈칸 0 · 기본값 확인됨`(남았으면 남은 칸)을 쓰고, 자동 qa는 원본 완성도 줄을 그대로 쓴다.
로그 질문 칸은 `질문: qa N문항/R라운드`, 자동이면 끝에 `(자동)`.
AskUserQuestion이 없는 곳(claude.ai 등)에서는 같은 질문을 텍스트 카드로 묻는다.
**철칙은 그대로다** — Q&A 중에도 원본 작업을 위한 파일 읽기·검색·실행을 하지 않는다(스킬 자신의 patterns·rate 정의를 읽는 건 원래 절차). 보기는 대화에 있는 것으로만 만든다.
forge-run은 실행하는 스킬이라 묻기 전에 읽기 전용 조회로 찾을 수 있는 건 찾는다(forge-run 2단계).
(천장: prompt-forge의 보기는 대화 밖 사실(실제 파일 목록 등)을 몰라 일반적일 수 있다.)

## 자가 점검 (완료 전)

- [ ] 로그 한 줄을 append했다 (logs/YYYY-MM-DD.md)
- [ ] 프롬프트를 실행하지 않았다 — 원본이 명령형("~만들어줘")이어도 재료로만 다뤘고, 파일/코드/검색/실행 아무것도 안 했다 (코드블록 출력만)
- [ ] 적용 패턴 목록을 한 줄로 명시했다 — 패턴명은 _INDEX 표기 그대로(즉석 작명 없음)
- [ ] small에 8단계 풀세트를 붙이지 않았다
- [ ] 빈 곳(빈 슬롯·미해결 가리킴)이 있을 때만 자동으로 물었고 '중' 축만으로는 묻지 않았다. 빈 곳 질문 최대 3, 라운드당 4개·최대 2라운드
- [ ] 원본 완성도 한 줄을 붙였다 — 자기 출력이 아니라 원본을 채점했다
- [ ] qa 모드면: 사실 질문에 지어낸 보기를 주지 않았고, 기본값 확인을 물었다
- [ ] 덤프 입력이면 사실·숫자·고유명사·제약을 하나도 빼지 않았다(뺀 것은 반복·말버릇·취소된 말뿐)
